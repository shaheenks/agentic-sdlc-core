# Why

`review_code`, `generate_tests` and `approve_design` are listed to developers and leads, pass
authorization and return their own input (inventory gap 1). A user or an agent that calls one gets
a fake result that looks like a real one. Reviews and tests are already produced by skills and the
reviewed document flow (FR-DOC-001). Real action tools belong with the write tools (version-03 P7,
FR-WRITE-001) and will be specified there under new IDs.

Decided by the user on 2026-11-10: retire them rather than hide them.

# Requirements

- Retires [FR-ACT-001](../requirements/functional/FR-ACT-001.md): `status: deprecated` and
  `implementation: parked`, because the code is gone. The file stays. A Notes line points to
  version-03 P7. The ID is never reused.

# Design

- [core_mcp](../components/core_mcp.md): delete the three tools from `sdlc_tools.py` and drop the
  FR-ACT-001 line from the concept. Update `mcp_servers/core_mcp/README.md`.
- [config](../components/config.md):
  - Remove the three tools from `tools.yaml`.
  - Remove their grants from `roles.yaml`: `developer` loses `generate_tests` and `review_code`, and
    `lead` loses `approve_design`.
  - Remove their `constraints` from `teams/payments.yaml`, `teams/sdlc-platform.yaml` and
    `teams/webapp.yaml`.
  - Remove their persona rows from `tests/policy/matrix.yaml`.
- [skills](../components/skills.md): `core/design-review` stops offering to record an approval with
  `approve_design`. `core/test-case-gen` stops calling `generate_tests` and returns the tests in
  the chat.

Effect on access:
- `lead` now differs from `developer` only by the data classification ceiling (`confidential`)
  and the `lead`-only skills.
- No team limits arguments in production config any more, because `github_get_file` and
  `bitbucket_get_file` are not constrained by any team today. This record does not add new
  constraints: that would narrow what users can read and is a separate decision.

Tests: about 100 test references use these tools as fixtures for argument limits, role
inheritance and audit. Tests about the policy engine move to a test-only catalog and team in
`tests/fixtures/config` that keeps one constrained tool with a `repo` argument, so argument limits
(FR-AUTHZ-002) stay covered. Tests about the real config are updated to the tools that remain.

Rollout: `config/` changes reach GCP only through `gcp_deploy.ps1 -Step config`, which the user
runs. Until then GCP dev still lists the tools, and calls fail because the code is gone. So the
image and the bundle should go out together.

As built: the fixture-only tools live in the shared test config overlay, `tests/support/config.py`
(next to the fixture-only members and source it already adds), not in a separate
`tests/fixtures/config` folder. `fixture_review` (developer) and `fixture_approve` (lead) take a
`repo` that each team limits to its own repositories, and the test MCP server registers echo
versions of both. The persona matrix loads the real catalog without them, and its rows for the
removed tools are replaced by rows on the connected tools. The startup check for a constrained
argument that is not a tool parameter is now tested on `github_get_file`.
