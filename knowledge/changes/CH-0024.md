# Why

Every deploy iteration is slow, because the image tag is the commit:

- `-Step images` builds and pushes all four images (core-mcp, user-agent, ingest, ui-copilotkit)
  one after another on every commit, including the Next.js build when only Python changed.
- `infra/gcp/main.tf` gives all four the same `var.image_tag`, so any commit changes every image
  reference. `plan` and `apply` then make a new Cloud Run revision (and job update) for every
  service, even those whose code did not change.

Raised by the user on 2026-11-15 while reviewing the test suite (CH-0023).

# Requirements

- Modifies [NFR-OPS-002](../requirements/non-functional/NFR-OPS-002.md) (still `draft`, from
  CH-0010), in its acceptance criteria:
  - `images`: an image is built and pushed only when its own build inputs changed. Its tag is
    derived from those inputs, not the commit.
  - `plan` and `apply`: run when `infra/gcp` changed or an image tag changed. Only services whose
    image tag changed get a new revision.
  - Record and rollback: the deploy records, and can redeploy, the tag of each image.

# Design

- [scripts](../components/scripts.md), `scripts/gcp_deploy.ps1`:
  - **Tag per image:** `Get-BuildTag <Dockerfile>` reads the Dockerfile's `COPY` sources (not
    `COPY --from`), adds the Dockerfile itself, and hashes `git ls-tree -r HEAD -- <inputs>` (path
    + blob id of every committed file) with SHA-256. The tag is `src-<first 12 hex>`. It is the same
    on every machine, needs no build, and still requires a clean tree (as today). Git-ignored
    files (`users.yaml`, `blocked.yaml`) are never inputs.
  - **`images`:** for each image, if `<registry>/<name>:<tag>` already exists
    (`gcloud artifacts docker images describe`), it prints `unchanged` and skips. Otherwise it
    builds and pushes. The oauth2-proxy mirror is skipped when present. `-Rebuild` forces every
    build. The summary prints each image's tag and whether it was built.
  - **`plan`:** computes the same tags, fails early if one is not in the registry ("run -Step
    images"), and passes them as `TF_VAR_image_tags` (JSON map `mcp`, `agent`, `ingest`, `ui`).
  - **`-ImageTag <tag>`** keeps working as an override that applies one tag to all four images,
    for re-planning or rolling back to tags pushed before this change.
  - `config` is unchanged: the bundle version still starts with the commit (FR-CFG-003).
- [infra_gcp](../components/infra_gcp.md): `variable "image_tags"` (map of string, validated to
  exactly the four keys) replaces `image_tag`. `local.images` uses one entry per service. Nothing
  else in the stack changes, so an unchanged image reference leaves its service's revision alone.
- Docs: `docs/guides/GCP_DEPLOYMENT.md` ("Image tag = commit SHA" becomes per-image tags) and the
  `gcp_deploy.ps1` line in `knowledge/rules/commands.md`.

Known effect: the core-mcp image bakes in `config/` and `skills/` (for standalone runs), so a
config change still makes a new core-mcp tag. On GCP, config comes from the bundle. Removing the
baked copy from GCP images is a possible follow-up, not part of this record.

Relation to CH-0010: the bash twin `scripts/gcp_deploy.sh` and the shared manifest it plans
should compute the tags the same way. Change detection there gets simpler, because
"did a tag change" replaces the path filter for `images`.

Alternatives considered:
- Keep the commit tag and retag unchanged images. It still needs a per-image notion of
  "unchanged", and every service's image string still changes, so revisions still roll.
- Docker image digests as the Terraform reference. Digests are known only after a build, so
  `plan` could not run without building.
