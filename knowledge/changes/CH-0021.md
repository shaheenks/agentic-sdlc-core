# Why

Phase WG.1; design decisions N7 to N10 and N13. The GCP stack identifies users by a Google ID token and takes
membership from Google Groups (synced from Entra to Cloud Identity) and `users.yaml`. The Entra stack keeps app
roles (CH-0011); both read one config catalog.

# Requirements

Applied when this record is approved; each goes back to `draft`. The wording becomes per stack, Entra criteria
kept as they are:

- [FR-IDN-001](../requirements/functional/FR-IDN-001.md) "Sign-in with Entra ID" becomes "Sign-in": the Entra
  stack requires a valid Entra token, the GCP stack a valid Google ID token; each refuses the other's.
- [FR-IDN-002](../requirements/functional/FR-IDN-002.md): on the GCP stack, teams and roles are the union of the
  configured Google Groups the user belongs to and `users.yaml` matched on email; token claims for groups or roles
  are ignored there.
- [FR-IDN-003](../requirements/functional/FR-IDN-003.md): `whoami(explain=true)` names the group or `users.yaml`
  entry behind each role; `config_explain` accepts group emails.
- [FR-IDN-004](../requirements/functional/FR-IDN-004.md): removing a user from a group revokes its roles within the
  configured cache time.
- [FR-AUTHZ-003](../requirements/functional/FR-AUTHZ-003.md): a role (workflow roles included) is bound to an app
  role, a group, or both.
- [FR-CFG-002](../requirements/functional/FR-CFG-002.md): `sdlc-config explain` accepts a persona, app roles, group
  emails or a direct member.
- [NFR-SEC-003](../requirements/non-functional/NFR-SEC-003.md): a Google ID token is accepted only with issuer
  `https://accounts.google.com`, an allowed audience, `email_verified` and an allowed `hd`; the user is `sub`.
- [NFR-PORT-001](../requirements/non-functional/NFR-PORT-001.md): another Cloud Identity domain is configuration
  (allowed domains, OAuth client IDs, group emails).
- [NFR-PRIV-003](../requirements/non-functional/NFR-PRIV-003.md): group email addresses may be committed in
  `config/`; tenant IDs, client secrets and user emails or UPNs stay in git-ignored env files.
- [NFR-MAINT-003](../requirements/non-functional/NFR-MAINT-003.md): tests also use a fake Google issuer and
  placeholder client IDs.

Rule sets changed with this record (binding text, reviewed with it): `knowledge/rules/configuration.md` (group
bindings), `knowledge/rules/security.md` and `knowledge/rules/tenants.md` (Google token checks, what may be
committed), and the "Nothing sensitive leaves its place" line in `CLAUDE.md` (group emails allowed in `config/`).

# Design

- [sdlc_auth](../components/sdlc_auth.md):
  - `sdlc_auth.google`: `GoogleTokenVerifier` (fastmcp `JWTVerifier` on `https://www.googleapis.com/oauth2/v3/certs`,
    issuer, audiences) plus the `email_verified` and `hd` checks; `principal_from_google_claims` (`sub`, `email`,
    `name`, `hd`); `google_verifier_from_env()` reading `SDLC_OAUTH_CLIENT_IDS` and `SDLC_ALLOWED_DOMAINS`.
  - `GroupDirectory`: `CloudIdentityGroups` with the service's own credentials. `direct` mode: for each group email
    in config, `groups.lookup` (cached) then `groups.memberships.lookup` for the user's email. `transitive` mode
    (Premium): one `groups.memberships.searchTransitiveGroups`. A TTL cache per user; a failed lookup returns no
    groups and logs without the email (fail closed). `StaticGroups` for tests and local runs.
  - `GoogleAdapter` (the `IdentityAdapter` of CH-0020): memberships are `group:<email>` keys.
- [config](../components/config.md): bindings in `roles.yaml`, `teams/*.yaml` and `sources/` may carry `group:
  <email>` beside `app_role:`; `platform.yaml` gains `identity.google` (allowed domains, `group_lookup` = `direct`
  | `transitive`, `group_cache_seconds`). `users.yaml` entries may carry `email` (GCP stack) beside `oid`. Schemas
  follow.
- [sdlc_config](../components/sdlc_config.md): the resolver matches membership keys of either kind; `validate`
  checks group emails are in an allowed domain; `personas.yaml` personas list both forms, and a parity check
  (`sdlc-config validate` and a test) fails when a persona resolves differently from its groups than from its app
  roles.
- [sdlc_policy](../components/sdlc_policy.md): unchanged rules; the policy suites run for both adapters.
