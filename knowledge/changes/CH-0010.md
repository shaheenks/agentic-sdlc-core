# Why

Deploying to GCP dev is manual today. The user runs `scripts/gcp_deploy.ps1` step by step, in an
order learned from experience: images, plan, apply, db, then config. Forgetting a step has caused
failures, for example a 403 because the config bundle was stale. The workflow platform (version-04)
adds many services, so manual rollout won't scale. The user asked, on 2026-11-11, for CI to deploy
every merge to `main` to GCP dev, with the steps run in sequence based on what changed.

This takes over the dev part of version-03 P3 ("CI deploy stages"). Production pipelines stay with
NFR-OPS-001.

# Requirements

- Adds [NFR-OPS-002](../requirements/non-functional/NFR-OPS-002.md) Continuous deployment to GCP
  dev.
- Modifies [NFR-MAINT-003](../requirements/non-functional/NFR-MAINT-003.md): the "no secrets, no
  cloud" rule now applies to the `ci` checks. A separate deploy workflow reaches GCP through
  Workload Identity Federation. NFR-MAINT-003 is back to `draft`.

# Design

- [ci](../components/ci.md): a new workflow, `.github/workflows/deploy-dev.yml`.
  - **Trigger:** `workflow_run` of `ci` completed with success on `main`, plus `workflow_dispatch`
    for rollback with inputs `config_version` or `image_tag`.
  - **Concurrency:** group `deploy-dev`, with `cancel-in-progress: false`, so merges queue up.
  - **Change detection:** diff the commit against the **last successful deploy**, read from a
    marker object `gs://<config_store_bucket>/deploys/dev/last`. The previous commit isn't enough,
    because a failed deploy's changes must be carried into the next one.

    | Step | Runs when these paths changed |
    |---|---|
    | `images` | `agents/`, `mcp_servers/`, `ingest/`, `libs/`, `ui/`, `**/Dockerfile`, `uv.lock`, `pyproject.toml` |
    | `plan` + `apply` | `infra/gcp/`, or `images` ran (the image tag is the commit) |
    | `db` | `db/` |
    | `config` | `config/`, `skills/`, or the tenant files' Secret Manager version changed |
    | `ingest` | `config/sources/` |
    | smoke checks | always |

  - **Steps:** one job with sequential steps in the order above; a failure stops the job.
    - It runs on `ubuntu-latest`, with bash only.
    - Tools: gcloud (`google-github-actions/auth` and `setup-gcloud`), Terraform (the version
      pinned as in the `ci` terraform job), uv and `jq`.
    - Each step is one `run:` line calling `scripts/gcp_deploy.sh <step>`. Change detection is a
      small bash script, `scripts/ci/changed_steps.sh`, which prints the steps to run.
  - **Plan guard:** after `plan`, `terraform show -json` is checked for `delete` or `replace`
    actions on stateful types (`google_sql_*`, `google_storage_bucket`, `google_secret_manager_*`).
    If any are found, the job stops, and a second job in the GitHub environment `gcp-dev-approval`
    (required reviewer: the user) applies the saved plan after approval.
  - **Smoke checks:** the MCP health endpoint, a 401 for a request without a token, the app URL,
    and `current` equal to the bundle just published.
  - **Record:** the job summary lists the commit, the steps run, the image tag and the config
    version. The marker is written only after the smoke checks pass.
- [scripts](../components/scripts.md): two deploy scripts with the same behaviour.
  - `scripts/gcp_deploy.sh` (bash, `set -euo pipefail`) is for GitHub Actions and Linux
    environments.
  - `scripts/gcp_deploy.ps1` stays the script for Windows.

  Both have:
  - **The same steps:** `state`, `base`, `config`, `images`, `plan`, `apply`, `db`, `ingest` and
    `urls`.
  - **The same flags,** spelled the native way for each shell:

    | bash | PowerShell |
    |---|---|
    | `--image-tag` | `-ImageTag` |
    | `--config-version` | `-ConfigVersion` |
    | `--auto-approve` | `-AutoApprove` |
    | `--tenant-from` | `-TenantFrom` |

    `--tenant-from secret-manager` loads the `ENTRA_*` values and the tenant files (`users.yaml`,
    `blocked.yaml`) from Secret Manager, instead of `.env` and `config/env/dev/`.
  - **The plan step** can save a JSON plan for the guard.
  - **No questions in CI:** without the auto-approve flag, both ask before changing anything, as
    today.

  Shared data lives in `scripts/deploy/manifest.json`, which both scripts read:
  - the step order and the path filters per step (also used by `changed_steps.sh`);
  - the image names and their Dockerfiles;
  - the oauth2-proxy mirror tag.

  So adding an image or a step is one edit. `shellcheck` runs on `scripts/**/*.sh`, and
  PSScriptAnalyzer runs on `scripts/**/*.ps1`, both in the `ci` lint job.
- [infra_gcp](../components/infra_gcp.md), in a new `infra/gcp/cicd.tf`:
  - a Workload Identity pool and a GitHub OIDC provider, restricted to this repository and `main`;
  - a `deploy` service account with the roles the steps need (Artifact Registry writer, Cloud Run
    admin, run jobs, storage on the config, state and deploy-marker buckets, Secret Manager
    accessor for the tenant values, and the IAM roles Terraform manages);
  - Secret Manager entries for the tenant values and tenant files.

  The user runs this bootstrap once by hand (`plan` and `apply`). After that, CI applies changes.
- Group map: not needed. Membership moves to app roles (CH-0011), so CI never handles a group ID.

Working rules: on approval, `knowledge/rules/commands.md` and `environments.md` are updated. CI
deploys dev on merge. People still run the first-time steps `state` and `base`, the CI/CD
bootstrap, approvals of destructive plans, Entra changes and production. The CLAUDE.md rule that
agents don't run Terraform or `gcp_deploy.ps1` themselves stays.

Alternatives considered:
- *Separate deploy jobs per step, with `needs:`.* That costs more runner setup and needs state
  passed between jobs (the plan file). One sequential job is simpler, and the approval job is the
  only split.
- *PowerShell only, using pwsh on the Linux runner.* It works, but the user asked for bash on
  GitHub Actions and Linux, with PowerShell kept for Windows.
- *Bash only, through Git Bash or WSL on Windows.* The user wants native PowerShell on Windows.
- *Two independent scripts.* They would drift. The shared manifest and the parity test keep them
  aligned.
- *Cloud Build triggered from GitHub.* That splits the pipeline across two systems. GitHub Actions
  already runs the checks.
- *Deploy on every push, without waiting for `ci`.* That could deploy a commit whose tests fail.

# Verification

- A config-only merge runs only `config` and the smoke checks; a code merge runs images, plan,
  apply and smoke; a migration merge also runs `db`.
- A merge after a failed deploy includes the earlier undeployed changes.
- A plan that would replace the Cloud SQL instance waits for approval.
- The `ci` workflow still has no secret and no cloud credential (`tests/infra`).
