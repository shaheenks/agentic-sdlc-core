# Why

The technical POC (version-00 to version-03) settled the system design. The user finalized it on
2026-11-11. The platform is a set of **workflows**, classified by source event, identity, access
to dependent systems and outcome delivery, and meant to be extended with new workflows and actions.
It follows the AI-Native SDLC Playbook (artifact chain, human gates, tiered autonomy) and the
Elephant-Goldfish Model (deep-context drafting, isolated review).

The current specification covers only the user-led workflow. It has one placeholder for
autonomous agents (FR-AUTO-001). This record makes the target design the specification, so later
work can be planned and traced against it.

The design: [docs/designs/workflow-platform.md](../../docs/designs/workflow-platform.md). The
system context is updated to match.

This change is specification and design only; no code changes. Implementation happens through
later change records, one per milestone. Each one names the requirements below that it builds.

# Design

The full design is in
[docs/designs/workflow-platform.md](../../docs/designs/workflow-platform.md). This section lists
how each touched component's design changes when the requirements are built.

- [core_mcp](../components/core_mcp.md):
  - accepts app-only workflow tokens (FR-IDN-005);
  - new tools `list_sources` (FR-SURF-004) and `claim_event` (NFR-REL-005);
  - skills also as MCP prompts or resources;
  - connector tools for real-time context (diff, pipeline log, logs) granted to workflow roles.
- [sdlc_auth](../components/sdlc_auth.md): `Principal.kind` (user or workflow), and app-only token
  validation bound to app roles.
- [sdlc_config](../components/sdlc_config.md):
  - new config kinds `Workflow` and `Trigger`, validated against roles, skills, tools and channels;
  - workflow roles;
  - `explain` for workflow principals.
- [config](../components/config.md): team roles `member` and `approver` (CH-0009), workflow roles
  and app-role bindings, the first `Workflow` and `Trigger` files.
- [sdlc_db](../components/sdlc_db.md): the code graph (entities and relations per source, under
  RLS), `agent_runs`, and image chunks with their locations.
- [ingest_bootstrap](../components/ingest_bootstrap.md): code parsing into the symbol graph, image
  understanding (opt-in, cached) and format-aware chunking.
- [ingest_loaders](../components/ingest_loaders.md): Office and SharePoint, OpenAPI and tabular
  loaders.
- [user_agent](../components/user_agent.md): declared as the `plan-design` workflow. It keeps
  using sessions only; memory is parked.
- [infra_gcp](../components/infra_gcp.md):
  - new Cloud Run services: event gateway, enrichment, workflow runtimes and delivery;
  - Cloud Run Jobs for the implementation sandbox (a Google ADK coding agent);
  - Pub/Sub topics and subscriptions;
  - workload identities with federated credentials;
  - the optional Agent Registry; the Agent Gateway only if the evaluation adopts it.

  The user runs the Terraform.

New components, each with its own concept when its record starts:
- `event_gateway` and `libs/sdlc_events` (version-03 P6 E1, E2);
- an enrichment service;
- `libs/sdlc_runner` and the workflow runtimes (`ci_agent`, `ops_agent`, `impl_agent`);
- a delivery service.

Alternatives considered:
- *Keep "autonomous agents" as one requirement.* It hides the different trust boundaries of
  intake, enrichment, agent and delivery.
- *Let the agent post its own results.* That gives the most exposed component a write credential
  (NFR-SEC-013).
- *Make the Agent Gateway the enforcement point.* That would split authorization across two
  places. The MCP server stays the authority, and the gateway may only narrow.

Decisions D1 to D7 were answered by the user on 2026-11-11. They are recorded in section 10 of the
design and applied to the requirements:
- D1: ops findings become Jira tickets or admin alerts.
- D2: the coding agent is built on Google ADK.
- D3: Kubernetes and Splunk push; pull comes later.
- D4: the roles are renamed to `member` and `approver`, and are team-scoped.
- D5: third-party platforms use A2A with the user's token.
- D6: the Agent Gateway is optional and will be evaluated.
- D7: memory is parked.

Still open: D8 (the Jira project per team and the admin alert channel) and D9 (accepting old and
new app-role values during the rename). Neither blocks approving the requirements.
