# Why

The user decided on 2026-11-11 (design D4) that team roles are `member` and an optional `approver`,
replacing `developer` and `lead`. They also confirmed that today's implementation leaks roles
across teams.

The resolver (`sdlc_config/resolver.py`) puts the roles from every team's membership into one flat
set, and then checks role-gated resources against that set. In the example config:

- Someone who is `lead` in webapp and `developer` in payments gets the confidential ceiling from
  webapp. They can then read the confidential rows of `payments-incidents`, a payments source.
- The same person sees payments' `ledger-design-review` skill (`access: { roles: [lead] }`),
  although they are not a payments lead.

Access to dependent systems is not affected: connected tools use the user's own credentials.

# Design

- [sdlc_config](../components/sdlc_config.md), in the resolver:
  - **Scoped roles:** roles are held as *scoped roles*: `(platform, role)` from global bindings
    and `(team, role)` from team membership. Inheritance expands within the same scope
    (`approver@payments` → `member@payments`).
  - **Tools:** a tool is allowed when any held role grants it. Its argument limits come only from
    the teams whose roles grant it, so a team that doesn't grant the tool never widens or narrows
    it (FR-AUTHZ-002 keeps holding). Platform grants follow today's rules, and `admin` stays
    unconstrained.
  - **Skills:** a team add-on skill whose `access.roles` names a role needs that role in the
    skill's own team.
  - **Sources:** a source's `access.roles` is matched against platform roles, and against team roles
    held in the source's `owner_team`. The classification ceiling is computed **per source**: the
    highest ceiling among platform roles and the roles held in that source's `owner_team`.
  - `EffectivePolicy.explain()` shows `role@team`, and `skill_decision` names the team a missing role
    belongs to.
- [config](../components/config.md):
  - `roles.yaml`: `developer` → `member`, `lead` → `approver`. `approver` inherits `member`.
  - The team files rename their membership roles and skill access roles.
  - App-role values become `SDLC.<Team>.Member` and `SDLC.<Team>.Approver`.
  - The persona matrix gains a cross-team persona: approver in webapp, member in payments.
  - Schema: a team role must not appear in a global binding, and a platform role must not appear in
    a team membership.
- [sdlc_db](../components/sdlc_db.md): the session context changes from one maximum classification
  to `(source, max_classification)` pairs. The query helpers set it per request, as today.
- [db](../components/db.md): a new append-only migration changes the RLS policies to compare each
  row's classification with the ceiling of *its own source*. `tests/db` gets a case for the
  cross-team persona.
- [core_mcp](../components/core_mcp.md): `whoami(explain=true)`, `config_explain` and the audit
  `roles` field show scoped roles (`approver@payments`). No tool changes.
- [scripts](../components/scripts.md): `entra_setup.ps1` defines the new app-role values. The
  tenant change is the user's, confirmed per action (`az account show` first).

Transition (design D9, decided 2026-11-11): switch in one step. The config binds only the new
app-role values. The user updates the Entra tenant (new app roles, user assignments moved, old
roles removed) and publishes the new config bundle in the same window. Users with an app-role
assignment get their access back on their next token, after a sign-in or refresh. Group-based
membership is not affected, because group aliases don't change. Each tenant action needs the
user's confirmation, with `az account show` checked first.

Order: after CH-0003, which also edits `roles.yaml`, the team files and the persona matrix.

Alternative considered: keep flat roles and prefix team roles in config (`payments-lead`). That
multiplies roles per team and still leaves the classification ceiling global.

As built:
- Platform roles count in every team. `admin` inherits `approver` at platform scope, so it keeps
  every team's approver-only skills and the `restricted` ceiling on every source.
- A global skill's `access.roles` (`design-review`: approver) is matched in any scope: it is not
  a team's resource.
- A tool that a platform role grants keeps today's limits (every member team that constrains it);
  a tool granted only through teams is limited by those teams alone.
- The role-scope check rejects a role that a team membership grants when a global binding (or a
  users.yaml global `roles` entry) already grants it.
- `EffectivePolicy.max_classification` stays as the highest ceiling for display; reads use
  `source_ceilings`. Migration 008 adds `sdlc.source_ceiling(source)`, read from the JSON setting
  `app.source_ceilings`.
- FR-AUTHZ-006 is `built`, not `live`: it becomes `live` once the GCP dev rollout is checked (the
  built and live split of CH-0001).
- Persona labels (`payments-dev`, `payments-lead`) are unchanged: CH-0011 reworks the personas
  when the groups go. Their app-role values use the new names.
- The persona matrix has the cross-team persona `cross-team-approver` (approver in webapp, member
  in payments). Before the resolver change its `ledger-design-review` and `payments-incidents`
  rows failed, which showed the leak.
