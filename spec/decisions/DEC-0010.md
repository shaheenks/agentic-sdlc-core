# Context

[DEC-0001](DEC-0001.md) and [DEC-0009](DEC-0009.md) make a Google account token the user's identity on every
surface: sdlc_ui runs a second, silent sign-in through its own OAuth client after IAP, and every service
verifies that token. Teams come from Cloud Identity groups, read with the Groups API.

For the first phases this costs more than it gives:

- sdlc_ui is the only surface in use. The agent runtime is called only by sdlc_ui, and user_agent_mcp only by
  sdlc_ui and the agent runtime.
- The second sign-in needs an OAuth client, refresh-token handling and a sealed session cookie in the BFF.
- Reading groups needs the Groups Reader admin role for each service account and, without Cloud Identity
  Premium, one lookup per mapped group.

# Options

## A. Keep DEC-0001 and DEC-0009 as they are

- For: one kind of user token for every surface; no service has to trust another's word about the user.
- Against: the costs above, before any surface but sdlc_ui exists.

## B. Forward the user from the IAP assertion between declared services (accepted)

sdlc_ui verifies IAP's signed assertion on every request and forwards the user's account ID and email in
headers. The agent runtime passes them on. user_agent_mcp accepts them only from service accounts declared in
configuration, each proven by its Google ID token for user_agent_mcp's URL, and each naming its surface.

- For: no OAuth client or second sign-in; sdlc_ui, the agent runtime and user_agent_mcp stay within the
  project; the user's own token switches back on through configuration (`identity.mode: oauth`) when another
  surface needs it.
- Against: sdlc_ui and the agent runtime become trust anchors, as DEC-0001 option A warned: a compromised
  caller can act as any user. Gemini Enterprise, which only supplies OAuth tokens, cannot be used meanwhile.

## C. Trust the user headers without proving the caller

- For: nothing to verify.
- Against: anything that can reach user_agent_mcp can be any user. Acceptable only on a developer's machine.

# Decision

**B**, accepted by the user on 2026-11-24, with **C** allowed only in the local environment.

- `identity.mode` in each environment's `identity.yaml` chooses: `caller_token` (B), `trusted_header` (C,
  refused by the configuration compiler and by the services outside `local`) or `oauth` (DEC-0001, off for now).
- The user travels as `X-SDLC-User-Id` (the Google account ID, `sub`) and `X-SDLC-User-Email`. sdlc_ui takes
  them from the IAP assertion it verified (signature, issuer and audience), never from IAP's unsigned
  `x-goog-authenticated-user-*` headers, and never forwards the assertion itself.
- A caller proves itself with `Authorization: Bearer <Google ID token>` of its service account, audience
  user_agent_mcp's URL; Cloud Run invoker IAM admits only those accounts as well. `identity.callers` maps each
  surface (`sdlc_ui`, `user_agent`) to its accounts.
- Artifacts, secrets and audit stay keyed by the account ID; teams, user groups and the block list are looked
  up by email, which must be in an allowed domain.
- Team roles and user groups are listed per user in `config/env/<env>/users.yaml`; Cloud Identity groups are
  not read.

# Consequences

- DEC-0001 and DEC-0009 are suspended, not withdrawn: their OAuth path stays in
  [Identity](../components/identity.md) behind `identity.mode: oauth`.
- [Directory](../components/directory.md) reads only configuration; adding someone to a team is a
  configuration change, published and activated like any other.
  [FR-TEAM-001](../requirements/functional/FR-TEAM-001.md) changes accordingly.
- [Gemini Enterprise Agent](../components/gemini-enterprise-agent.md) and
  [FR-SURF-003](../requirements/functional/FR-SURF-003.md) wait for mode `oauth`.
- The calls stay made for the user ([FR-IDN-002](../requirements/functional/FR-IDN-002.md)): every tool call
  is scoped to and audited for the forwarded user, together with the caller that vouched for them.
