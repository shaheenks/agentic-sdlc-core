# Context

[DEC-0015](DEC-0015.md) built phase 5a as an unattended chain. A person merges the design, and the merge event starts
ci_workflow_agent, which plans as the system identity. A merged plan then starts the implementation, built in the
Code Workspace with the machine user's PAT. That chain is deployed on development (2026-11-26), but no webhook is set
up yet, so no event reaches it.

On 2026-11-28 the user asked for two changes:

- **Plan and implement move to user_agent.** They become stages like features and stories and the design, run in
  chat with the user.
- **sdlc_ui simulates events.** It gets a way to send events to ci_workflow_agent and operations_agent until all the
  webhooks are set up.

Today user_agent's stages ([FR-SDLC-002](../requirements/functional/FR-SDLC-002.md) to
[FR-SDLC-005](../requirements/functional/FR-SDLC-005.md)) work like this:

- they draft with a skill and review in a fresh context;
- the drafts stay the user's own until the user asks for a write;
- then they open a pull request on the control repository with the user's connection;
- they wait for a person to merge it, and check the approval through user_agent_mcp
  ([DEC-0012](DEC-0012.md), [DEC-0013](DEC-0013.md)).

The Code Workspace runs only for event_agent_mcp. It clones and pushes with the machine user's PAT.

# Options

The two changes are the user's. The options below cover what they leave open.

## How a user's implementation is built and pushed

The run is the user's, so every call to GitHub must be made as the user. The user's PAT lives encrypted in the
artifact bucket ([DEC-0006](DEC-0006.md)), and only user_agent_mcp can decrypt it.

- **A. Give the job the user's PAT.** Job overrides are visible in the execution's metadata, and the job would need
  the key to every user's secrets. Rejected.
- **B. The job clones with the machine user's PAT.** The user's run would read code as the system identity. This
  breaks "calls are made as the user". Rejected.
- **C. user_agent_mcp fetches, the job only builds (chosen).** user_agent_mcp downloads the feature branch's
  archive with the user's connection and writes it, with the change set, into the run's folder. A second job
  definition, `code-workspace-user`, built from the same image and holding no secret, unpacks the archive, applies
  the change set and runs the declared commands. It writes the results next to them. user_agent_mcp then commits the
  change set to `sdlc/<control-id>/<repo>` through the provider's API and opens the pull request, both with the
  user's connection.

## The unattended plan and implement workflows

- **A. Retire them at once.** Then nothing on development would be left for the event simulation to send events to
  before phase 5b's reviews exist.
- **B. Keep them until user_agent's stages are built, then retire them (chosen).** The simulation is tested first on
  `ci_plan` and `ci_implement`, which are already deployed. Once the user's stages pass their gate, both
  subscriptions and both workflows are removed. ci_workflow_agent keeps the event path for phase 5b.

## How sdlc_ui sends a simulated event

- **A. sdlc_ui signs a fake webhook with the webhook secret.** sdlc_ui would hold the secret, and the event would
  not record who sent it. Rejected.
- **B. A separate simulation endpoint on the gateway (chosen).** sdlc_ui calls `POST /simulate` with its service
  account's ID token and the forwarded user, as it already does for user_agent_mcp ([DEC-0010](DEC-0010.md)). The
  gateway checks three things:
  - the caller is a declared caller of the `sdlc_ui` surface;
  - simulation is allowed in this environment;
  - the user is a member of the team the event is for.

  It then builds the event from the form, marks it `simulated` with the user who sent it, and passes it through the
  same triage, deduplication and Cloud Tasks hand-off as a verified webhook.

# Decision

**Accepted by the user on 2026-11-28.**

## Plan and implement as user_agent stages

The agent offers four new workflows, each called as a tool in chat, after `hand_off_design`:

1. **`implementation_plan`** drafts `plan-<repo>.md` for one target repository the design names. It uses the
   `implementation-plan` skill and reads the merged design, the stories (their Jira keys in `links.yaml`) and the
   repository's code within the drafting budget. It then runs the fresh-context review loop with the readiness
   reviewer, like the other stages. The plan stays the user's own artifact.
2. **`hand_off_plan`** runs only when the user asks for it.
   - It checks with user_agent_mcp that `design.md` was merged by a person on `feature/<control-id>`.
   - It opens `plan-<repo>.md` from `sdlc/<control-id>/plan-<repo>` into the feature branch on the control
     repository, with the user's connection.
   - It waits for a person to merge it and checks the approval, as the design hand-off does.
3. **`implementation`** starts from a plan merged by a person.
   - It drafts the change with tests, using the `implementation` skill.
   - It runs the repository's declared `workspace` commands through user_agent_mcp's `workspace_run`, and fixes
     failures within the run's limits ([FR-WFL-005](../requirements/functional/FR-WFL-005.md)).
   - It shows the user the change, the results and any departures from the plan. The user can ask for changes,
     which start another round.
4. **`open_implementation`** runs only when the user asks for it.
   - It lists the target repository's open pull requests and does not open a second one.
   - It commits the change set to `sdlc/<control-id>/<repo>`.
   - It opens the pull request into the target repository's `feature/<control-id>` with the user's connection,
     tagged with the Jira keys and linking the design and the plan.
   - The repository's CI runs on it, and a person merges it.

Rules that stay as in DEC-0015:

- The agent pushes only `sdlc/` branches, and nothing merges or approves.
- No plan is opened without a design merged by a person, and nothing is implemented without a plan merged by a
  person.
- A repository with no `workspace` commands is proven by its CI alone.

## user_agent_mcp

- Tool group `implementation` on the `user_agent` surface (sdlc_ui gets it too, so that it shows the results):
  - `plan_open_pull_request` and `implementation_open_pull_request`, which share their checks with event_agent_mcp
    through `libs/sdlc_control`;
  - `workspace_run`;
  - `repo_archive`, internal to `workspace_run` and not offered to the model.
- Run folders sit under `artifacts/users/<user>/runs/<run-id>/` and are deleted after 7 days. user_agent_mcp may run
  `code-workspace-user` only, never the system job.

## Code Workspace

- The job `code-workspace-user` runs the same image with no secret and no git credentials. It needs package registry
  egress only, which is still unrestricted as in DEC-0015.
- Only user_agent_mcp's service account can start it.
- The system job stays unchanged for phase 5b.

## Simulated events

- Which teams may simulate is declared per environment: `simulation: {teams: [...]}` in `config/env/<env>/system.yaml`.
  Without that entry, the gateway refuses every simulation.
- sdlc_ui gets an **Events** page, shown only where simulation is on. It lists the subscriptions of the team the user
  picks, with any agent (ci_workflow_agent and operations_agent).
  - For a pull request event, the form takes the repository, the pull request number and the action. The gateway
    reads the pull request's base, merge state and merged-by from the provider with the machine user's connection,
    so the event carries facts, not what the form claims.
  - Other event kinds (builds, rollouts, alerts) are entered as metadata.
- The delivery ID is `sim-` plus a hash of the event's facts (for a pull request: repository, number, action and
  merge commit), so the same event is claimed once, as the exit gate requires. The audit record and the run's state carry `simulated: true` and the user who sent
  it.
- The approvals stay real: event_agent_mcp still checks the merge on the control repository, so a simulated event
  cannot plan an unmerged design.
- operations_agent has no subscriptions yet. Its first one, in phase 6, appears on the Events page with no change to
  the mechanism.

## Exit gate

- **Simulation:** on development, before the webhook exists, a simulated merge of a tasklist design from sdlc_ui
  produces one plan pull request. A second simulation of the same pull request starts no second run. A user outside
  the team, or an environment without `simulation`, is refused.
- **Interactive plan and implement:** in chat, from that merged design, user_agent drafts and reviews the plan and
  opens it as the user. After a person merges it, user_agent builds the change in `code-workspace-user`, shows the
  results and opens the implementation pull request as the user. Its build and tests pass in the workspace and in CI.
- **Retirement:** `ci_plan` and `ci_implement` are then removed.

# Consequences

- **Requirements to change on acceptance:**
  - FR-SDLC-006 becomes "Implementation plan and implementation with the user": user_agent, the user's connection,
    approvals at each merge.
  - FR-SDLC-005: the merge of `design.md` approves it for the plan stage instead of starting ci_workflow_agent.
  - FR-TRIG-001 gains simulated events.
  - New FR-TRIG-006, "Simulated events": who may simulate, facts read from the provider, marked and audited.
- **Components:**
  - user_agent satisfies FR-SDLC-006; ci_workflow_agent drops it after the retirement.
  - sdlc_ui and event_gateway satisfy FR-TRIG-006.
  - code-workspace and user-agent-mcp gain the user mode.
- **New resources on development**, each applied only after the user approves its plan:
  - the job `code-workspace-user` and its runner IAM for user_agent_mcp;
  - objectUser for user_agent_mcp on `artifacts/users/`, if it is not already granted;
  - the gateway's read of the machine user's PAT, for the pull request facts;
  - the gateway is already public, so `/simulate` checks sdlc_ui's ID token in the application, and no invoker
    is added.
- **The plan document:** phase 5a's interactive part becomes milestones 7 to 10, and the exit gate is the one above.
  The webhook on the control repository is still added later, with no code change.
