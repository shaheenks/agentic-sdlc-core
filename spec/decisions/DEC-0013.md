# Context

Under [DEC-0012](DEC-0012.md) a feature and its stories reach Jira only after a person merges their pull request into
the control repository's main branch, and Jira holds two levels (the team's feature type and its stories). Running it
on development showed three gaps:

- Every feature waits for a merge into main before anything reaches Jira, and a retry after a Jira refusal opened new
  pull requests.
- Jira items are created without looking at what is already open: no epic, duplicates of open features and stories.
- The design, plan and implementation of one feature land on main one by one, with nothing tying them together.

On 2026-11-26 the user asked for every feature to sit under an epic and every story under a feature, for open issues
to be found and reused while drafting, for a missing epic to be suggested or created on the user's behalf, for an
approved feature to get its own branch on the control and target repositories, and for pull request approvals to be
checked against that feature branch, not main. They chose:

- **Hierarchy:** Epic → Feature → User Story, with the user stories as Jira **sub-tasks** of the feature (no Jira
  administration or Premium plan needed).
- **Jira timing:** the issues are created **once the user approves in chat**; no pull request merge is needed for
  this write.
- **Branches:** **every** later pull request (design and plan on the control repository, implementation on the target
  repositories) merges into the feature branch; a person merges the feature branch into main when the feature is
  done.
- **No epic:** the workflow **suggests** one and creates it only after the user confirms.

# Options

## A. Keep DEC-0012 (merge into main approves each artifact)

- For: every write rests on a merged pull request; one branch to reason about.
- Against: the gaps above.

## B. Chat approval opens a feature branch; Jira hierarchy with reuse; approvals on the feature branch (chosen)

- For: one place per feature (its branch) holds every artifact and the record of every write; Jira gets a coherent
  hierarchy with no duplicates; the user approves a feature where they drafted it; the design, plan and code of a
  feature are reviewed together before main.
- Against: the first Jira write rests on the run's own user's approval in chat, not on a second person's merge
  (separation of duties moves to the design and later pull requests); user stories as sub-tasks cannot be planned in
  sprints on their own, and story points on sub-tasks need the field on the sub-task screen; feature branches must
  be merged to main by a person and can drift from main.

## C. Feature branch only on the control repository

- For: product repositories keep their flow.
- Against: implementation pull requests would not be tied to the feature until main; the user chose all
  repositories.

# Decision

**B**, accepted by the user on 2026-11-26.

## Drafting: finding what is open

- While drafting features and stories, user_agent searches the team's Jira project for open epics, features and
  stories related to the brief, and the draft names them: the epic the feature belongs to, an open feature it
  extends instead of a new one, and open stories it would duplicate (left out or adopted).
- If no open epic fits, the draft proposes one (summary and description). The epic is created only after the user
  confirms it in chat.

## Approval in chat, then the feature branch and Jira

When the user approves the feature and its stories in chat (a human task bound to the run,
[FR-HUM-001](../requirements/functional/FR-HUM-001.md)):

1. **Control repository:** a branch `feature/<control-id>` is created from main, and `features/<control-id>/feature.md`
   (the feature and its stories, with front matter naming the user who approved and when) is committed to it as the
   user. This commit is the record of the approval and comes before any Jira write.
2. **Jira**, as the user, reusing what exists:
   - the epic: the one chosen, or the proposed one if the user confirmed it;
   - the feature: an issue of the team's feature type whose parent is the epic, unless an open feature of the same
     summary exists (it is used instead);
   - the stories: sub-tasks of the feature, each with its story points and acceptance criteria, unless an open
     sub-task of the same summary exists.
3. **Record:** the keys (epic, feature, stories) and links go into `links.yaml` on the feature branch.
4. **Target repositories:** the same branch `feature/<control-id>` is created from each target repository's default
   branch, so later implementation pull requests have their base.

A failure after step 1 is retried with the same control ID: the branch and the approval are reused, nothing is
created twice.

## Pull requests and approvals on the feature branch

- The design specification goes to the control repository as a pull request **into** `feature/<control-id>`; so do
  the implementation plans. Implementation pull requests go into `feature/<control-id>` on each target repository.
- **Approved** means: the artifact is on the feature branch, and the last commit that changed it there came from a
  pull request into the feature branch merged by a person who is not a system identity. The check that DEC-0012 made
  against main is made against the feature branch.
- The hand-off to ci_workflow_agent is the merge of `design.md` into the feature branch.
- A person merges the feature branch into main when the feature is done; no agent merges it.

## Configuration

Each Jira project entry gains `epic_type` (default `Epic`); `feature_type` defaults to `Story` and `story_type` to
`Sub-task` (`Subtask` in team-managed projects, configurable); stories join their feature as parent. The existing
duplicate and approval checks stay.

# Consequences

- Amends [DEC-0012](DEC-0012.md): the feature and its stories are approved in chat (recorded by the
  commit on the feature branch), not by a merge into main; every later approval is checked on the feature branch.
  Everything else in DEC-0012 (the control repository, `links.yaml`, records of unattended writes, no Jira status
  gates) stays.
- Requirements changed with the acceptance: FR-SDLC-001 (approvals on the feature branch), FR-SDLC-002 (open issues
  reused, epic suggested, chat approval, hierarchy, sub-tasks), FR-SDLC-003 (design from the feature branch),
  FR-SDLC-005 (design pull request into the feature branch), FR-SDLC-006 (plans and implementation pull requests into
  the feature branches), FR-SDLC-013 (layout and approval on the feature branch), FR-HUM-005 (the chat approval is
  bound to the write).
- Code: connectors create branches and commit to a named branch; user_agent_mcp gains a tool that opens the feature
  branches and records the approval, and its Jira tool creates the hierarchy with reuse; the publish workflow becomes
  "approve in chat, then branch and Jira"; the design hand-off targets the feature branch; the approval check takes
  the feature branch.
- The users' tokens need to create branches on the control and target repositories.
