# Context

Users are Google accounts in the organisation's Cloud Identity account, provisioned from Microsoft
Entra ID and signing in through Entra ID by SAML single sign-on
([FR-IDN-001](../requirements/functional/FR-IDN-001.md)). sdlc_ui needs two things:

1. **A perimeter.** Only the organisation's users in the declared access groups should reach it.
2. **A user token.** The BFF calls the platform's services as the user
   ([FR-IDN-002](../requirements/functional/FR-IDN-002.md)). That token should be the same kind the
   Gemini Enterprise app passes to the platform's agent: a Google-issued OAuth token for the signed-in user
   ([FR-SURF-003](../requirements/functional/FR-SURF-003.md)). Then the [Identity](../components/identity.md)
   component verifies one token family for every surface.

## Constraints

- Gemini Enterprise is the only AI surface for now ([FR-SURF-005](../requirements/functional/FR-SURF-005.md) and
  [FR-SURF-006](../requirements/functional/FR-SURF-006.md) are parked), so sdlc_ui is the one place for
  connections (PAT entry, [FR-CONN-005](../requirements/functional/FR-CONN-005.md)), artifacts and run views. It
  needs a user token for user_agent_mcp, so option A alone does not work.
- Sessions, artifacts and secrets are per user ([FR-AUTHZ-008](../requirements/functional/FR-AUTHZ-008.md)),
  keyed by the Google account ID (`sub`), not by a token. After a sign-in expires the user signs in again and
  finds their sessions ([FR-WFL-009](../requirements/functional/FR-WFL-009.md)).
- There is no operations database ([DEC-0003](DEC-0003.md)), so the BFF cannot keep refresh tokens in a server
  session store. They go in an encrypted, HTTP-only, same-site session cookie, sealed with a key from Secret
  Manager, so any Cloud Run instance can serve any user.
- sdlc_ui's own OAuth client is independent of the client IAP uses, because the second, silent sign-in relies
  only on the Google session.

# Options

## A. Identity-Aware Proxy only

Turn on IAP directly on the sdlc_ui Cloud Run service. IAP signs users in with their Google account (so
through Entra ID), checks IAM group access and passes a signed `x-goog-iap-jwt-assertion` header.

- For: no sign-in code in the BFF; unauthenticated traffic never reaches the container; access by
  IAM group; no load balancer needed.
- Against: the BFF gets only an identity assertion, whose audience is sdlc_ui's own IAP resource. It is
  not a token the BFF can present to other services. The platform's services would have to trust the BFF's word
  about who the user is, which makes the BFF a trust anchor and breaks "calls are made as the user".

## B. Internal OAuth app only

Register sdlc_ui as an OAuth client in a Google Cloud project of the organisation, with user type
*Internal*, so only accounts of the Cloud Identity account can sign in. The BFF runs the OpenID
Connect authorization-code flow with Google; because Cloud Identity federates to Entra ID, the user
sees Entra ID sign-in once.

- For: the BFF holds the user's Google ID and access tokens and forwards them, the same token family
  Gemini Enterprise passes; refresh tokens keep long sessions working.
- Against: sign-in, session and refresh code in the BFF. The service must accept unauthenticated
  traffic, so every route depends on the BFF getting it right.

## C. Both (accepted)

IAP is the perimeter (option A); after IAP admits the user, the BFF runs the internal OAuth app flow
(option B) to get the user's tokens. The Google session from the IAP sign-in makes the second step
silent in normal use.

- For: defence in depth (unauthenticated or out-of-group traffic is stopped before the container),
  and a real user token for every backend call.
- Against: two pieces of configuration (the IAP access list and the OAuth client) that must agree,
  and a redirect on first visit.

## Not considered further

- **IAP external identities (Identity Platform):** meant for customer identities; IAM cannot gate
  access, so the app would filter on claims itself. It does not fit workforce users.
- **Workforce Identity Federation instead of Cloud Identity:** ruled out by the choice of Cloud
  Identity accounts federated from Entra ID.
- **Custom SAML apps in the Google Admin console:** they make Google the identity provider for a
  third-party app. sdlc_ui is Google-native and does not need one. The Entra ID side does use an
  enterprise app, Microsoft's Google Cloud / Google Workspace connector, for provisioning and SAML
  single sign-on into Cloud Identity.

# Decision

**C**, accepted by the user on 2026-11-22, with these details:

- Platform services accept Google access tokens issued to the declared OAuth clients (sdlc_ui's, the Gemini
  Enterprise authorization's), with the `openid` and `email` scopes so the user ID and account can be checked.
- A verified token is cached per service instance for 300 seconds, or until it expires if sooner. Only the first call with a token pays Google's verification round trip, which keeps
  [NFR-PERF-001](../requirements/non-functional/NFR-PERF-001.md) within reach; a disabled user or a revoked
  token keeps working for at most 300 seconds on an instance that has already cached it.
- The BFF keeps the user's tokens in an encrypted session cookie, not on the server.
- sdlc_ui uses its own OAuth client, whichever client IAP uses.
- IAP protects the Cloud Run service directly, and the Gemini Enterprise authorization requests the `openid`
  and `email` scopes.

# Consequences

- [Identity](../components/identity.md) verifies Google-issued tokens for every surface. It verifies
  ID tokens locally against Google's keys and access tokens by token introspection, with caching.
  Either way it accepts a token only when it was issued to one of the platform's OAuth clients (sdlc_ui's
  client, the client of the Gemini Enterprise authorization) and belongs to the organisation's Cloud
  Identity account.
- [GCP Foundation](../components/gcp-foundation.md) defines in Terraform the IAP settings, the IAP
  access groups and the OAuth clients. Client secrets go to the secrets store.
- [DEC-0009](DEC-0009.md) confirms that IAP is perimeter enforcement only and Google account tokens are the
  user's identity on every surface.
- [NFR-SEC-007](../requirements/non-functional/NFR-SEC-007.md) captures the perimeter and
  [NFR-SEC-003](../requirements/non-functional/NFR-SEC-003.md) keeps the tokens in the BFF.
