# Context

Phase 4a is done: from sdlc_ui, a feature approved in chat opens `feature/<control-id>` on the team's control and
target repositories, its Jira hierarchy is created, and the design specification reaches that branch as a pull request
([DEC-0013](DEC-0013.md)). Phase 5 picks the work up when a person merges that design: a plan per target repository,
then an implementation pull request per repository, then two review workflows on every pull request. None of the event
side exists yet: `event_gateway/`, `mcp_servers/event_agent_mcp/`, `code_workspace/` and
`event_based_agents/ci_workflow_agent/` are skeletons, and `infra/gcp` has no event resources.

On 2026-11-26 the user chose:

- **Split:** 5a builds the path from a merged design to an implementation pull request; 5b adds the security and
  quality review workflows, Jira tasks for their findings and CI failure explanations.
- **System connection:** a separate GitHub machine user with a fine-grained PAT, so a merge by a person is never
  confused with the agent's own work.
- **Webhooks:** a public Cloud Run URL; every delivery is verified by its signature before anything else.
- **Build and test commands:** declared per repository in team configuration.

# Options

The four choices above were made by the user; the options here are the ones left open by them.

## Starting a run from a webhook

GitHub waits 10 seconds for a webhook answer and an ADK run takes minutes.

- **A. The gateway streams the run in the request.** Against: the webhook times out and GitHub redelivers.
- **B. Pub/Sub push to a run endpoint.** Against: a push is acknowledged within at most 600 s, so a long run is
  redelivered while it is still going.
- **C. Cloud Tasks (chosen).** The gateway verifies, deduplicates and triages the delivery, enqueues one task and
  answers `202` at once. The task calls the gateway's internal `/run` endpoint with an OIDC token (dispatch deadline
  up to 30 minutes, retried on failure), which starts the run on the event agents' Agent Runtime and follows it. The
  run's session ID is derived from the delivery ID, so a retried task resumes the same run instead of starting a
  second one.

## Where the subscriptions live

- **A. In code.** Against: [FR-TRIG-001](../requirements/functional/FR-TRIG-001.md) asks for subscriptions declared in
  configuration.
- **B. `subscriptions.yaml` in shared configuration (chosen).** Each subscription names its workflow, the event
  (provider, type) and filters on metadata (the repository role, `control_repo` or `repository`; the base branch
  prefix; merged or not), the writes it may make without approval, and its run limits. The gateway reads the active
  bundle like every other service.

# Decision

**Accepted by the user on 2026-11-26.**

## The chain on the feature branches

1. A person merges the design pull request into `feature/<control-id>` on the control repository. GitHub sends
   `pull_request` `closed` with `merged: true` and base `feature/<control-id>`.
2. The gateway matches it to the `ci_plan` subscription (repository is a team's `control_repo`, base branch
   `feature/`, merged) and starts ci_workflow_agent. The run checks through event_agent_mcp that `design.md` was
   merged by a person ([FR-SDLC-001](../requirements/functional/FR-SDLC-001.md)) and that no plan pull request is
   open for it.
3. For each target repository the design names, the agent drafts `plan-<repo>.md` from the design, the user stories
   (Jira keys in `links.yaml`) and the repository's code, and opens it as a pull request into
   `feature/<control-id>` on the control repository, from the working branch `sdlc/<control-id>/plan-<repo>`.
4. A person merges a plan pull request. The `ci_implement` subscription starts a run for that repository: the agent
   reads the plan and the code, writes the change with tests, and runs the repository's build and tests in the Code
   Workspace, fixing failures within the run's limits.
5. It pushes `sdlc/<control-id>/<repo>` and opens the implementation pull request into `feature/<control-id>` on the
   target repository, tagged with the Jira keys, linking the design and the plan. The repository's own CI runs on it.
6. Every pull request and write is recorded on the control repository's feature branch (`links.yaml`,
   `records/`). If the plan cannot be built as written, the agent comments on the pull request and stops.

Merges stay with people; no tool merges, approves or pushes to `main` or `feature/*`.

## event_gateway

- Cloud Run in europe-west3, ingress `all`, unauthenticated invoke on `/webhooks/<provider>` only. Each delivery is
  verified first (GitHub: `X-Hub-Signature-256` HMAC with the webhook secret from Secret Manager); an unverified
  delivery is refused and audited before its body is parsed further.
- Deduplication: one object per delivery ID created only if absent (`ifGenerationMatch=0`) under `events/` of the
  artifact bucket ([DEC-0003](DEC-0003.md)), deleted after 7 days.
- Triage by metadata against `subscriptions.yaml`; unmatched events are audited as ignored. `/run` accepts only Cloud
  Tasks' OIDC token for the gateway's own service account.
- Bitbucket and Jira webhooks follow in 5a's later milestones with their own verification; Google Cloud events come
  with phase 6.

## event_agent_mcp

- Cloud Run, internal ingress, invoker only for the event agents' Agent Runtime service account; verifies its Google
  ID token on every request (the system identity, [FR-IDN-004](../requirements/functional/FR-IDN-004.md)).
- The system identity's grants are declared in configuration as `system.yaml` of the environment (tool groups,
  sources, the teams it may act for) and resolved by the Access Policy like a user's.
- Tools for 5a: read the control repository's feature artifacts and approvals; read repository files and list pull
  requests; open a plan or implementation pull request (only from `sdlc/` branches into `feature/` branches);
  comment on a pull request; record on the control repository; run the Code Workspace. Each write is declared in the
  subscription as allowed without approval ([FR-TRIG-003](../requirements/functional/FR-TRIG-003.md)).
- System connection: the machine user's fine-grained PAT (Contents and Pull requests: write on the control and target
  repositories; no administration), a Secret Manager secret given as an environment variable
  ([FR-CONN-004](../requirements/functional/FR-CONN-004.md)). The machine user's login is declared per provider in
  the environment configuration, and approval checks refuse a merge made by it.
- Shares the connectors, policy, audit and control-repository code with user_agent_mcp through `libs/` (the control
  logic moves from user_agent_mcp into a library).

## Code Workspace

- A Cloud Run job with its own service account, runnable only by event_agent_mcp's service account. Each execution
  gets the repository, the working branch, and the path of the change set under `artifacts/system/<run-id>/` (too
  large for job overrides); it checks out the feature branch, applies the change set, runs the declared commands,
  pushes the working branch, and writes the results (exit codes, test summary, trimmed logs) back next to the change
  set.
- It refuses to push anything but an `sdlc/` branch, starts clean every execution and keeps nothing.
- Commands per repository in team configuration: `workspace: {setup, build, test}` on a `repositories` entry;
  a repository without `workspace` gets its implementation pull request without a local build, and CI alone proves
  it. They run in the platform's image with Python and Node.js; an image per repository (a job per image) is later.
- Egress goes through the existing Cloud NAT. Limiting it to the declared Git hosts and package registries (Secure
  Web Proxy or firewall policies) is deferred; until then the job holds only the machine user's PAT and runs nothing
  but the declared commands.

## ci_workflow_agent

- An ADK graph workflow on its own Agent Runtime deployment ([DEC-0007](DEC-0007.md)), with two entry workflows,
  `plan` and `implement`, and no human tasks. Skills: `implementation-plan` and `implementation`. Models as for
  user_agent (`gemini-3.8-flash` in `eu`). The plan gets one fresh-context review round before its pull request.
- Run limits from the subscription: Code Workspace iterations (default 5), files read, and wall time (25 minutes,
  inside the Cloud Tasks deadline).

## Exit gate for 5a

On the tasklist team's test control and target repositories on GitHub: merging a design pull request into its feature
branch produces one `plan-<repo>.md` pull request there; merging that produces one implementation pull request into
the target repository's feature branch whose build and tests pass in the Code Workspace and in the repository's CI;
a redelivered webhook starts no second run; an unsigned delivery is refused; nothing is merged by the agent.
