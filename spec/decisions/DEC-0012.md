# Context

[DEC-0008](DEC-0008.md) made Jira the record of approved features and stories, approval in chat their gate,
and a design pull request on the first target product repository the hand-off to ci_workflow_agent. That
leaves no single place that shows what the agents did in Jira, Confluence and the repositories, and from which
approved artifact.

On 2026-11-25 the user asked for one `sdlc-control` repository per team, for user_agent and the event-based
agents alike, and chose:

- **When.** A user drafts and continues with their own artifacts (the [Artifact Store](../components/artifact-store.md))
  for as long as they like, with no check on sdlc-control. Only when they ask for a write to Jira, Confluence or
  a repository do the artifacts it rests on go to sdlc-control for approval.
- **Approval** is a person merging the artifact's pull request on sdlc-control.
- **Every action on an external system** is recorded on sdlc-control.
- **Each later step** that starts from published items looks for them on sdlc-control's main branch. A step
  that continues from the user's own artifacts needs no such check.
- **The design specification** lives only in sdlc-control; product repositories receive the implementation
  pull requests only.
- **The record** of an action is the artifact committed before it, plus the resulting keys and links recorded
  after it (no separate per-action records).
- **Confluence** stays after phase 4a; these rules cover Confluence writes when it comes.
- **Team information** (Jira projects, Confluence spaces, repositories, control repository) is declared per
  environment in `env/<env>/teams.yaml`, as are user groups and sources.

# Options

## A. Keep DEC-0008: Jira and the product repository

- For: built on systems teams already use; no extra repository.
- Against: no single record of agent writes or of the artifacts they came from; chat approvals are visible
  only to the run's user.

## B. Approval on sdlc-control for every artifact, written or not

- For: every artifact is reviewed and versioned.
- Against: every draft waits for a merge, even exploratory work that never leaves the user.

## C. A per-team sdlc-control repository that gates and records external writes (chosen)

- For: drafting stays fast and private; every write to another system rests on an artifact a person approved,
  in one reviewable, versioned place per team; approval by merge keeps "no agent approves or merges its own
  work" and uses the repository host's own branch protection and reviewers; the event-based agents read one
  declared repository.
- Against: one more repository per team, and a connection with write access to it for every user who publishes;
  a publishing step waits for a merge; links recorded after an action are a direct commit that branch
  protection must allow for the acting identity.

## D. Records in the platform's own store

- Against: a store the platform does not have ([DEC-0003](DEC-0003.md)); hidden from people who do not use the
  platform.

# Decision

**C**, accepted by the user on 2026-11-25.

## Configuration

- `env/<env>/teams.yaml` gives each team its `systems`: lists of Jira projects (`jira`), Confluence spaces
  (`confluence`) and product repositories (`repositories`), each with one default that a write uses when the
  user names none, and `control_repo` (`provider`, `repo`, `branch`). Any `org/repo`
  will do (such as `example-org/sdlc-control`); no two teams share one. The compiler refuses a team with a Jira project or repositories but no control
  repository.
- Teams, user groups and sources, with what they are given, are environment configuration
  (`config/env/<env>/`). Environment folders are git-ignored, so site URLs, teams and their grants stay out of the
  repository.

## The repository

One folder per feature, named by a control ID the agent assigns when the first artifact is published
(`F-<yyyymmdd>-<slug>`), since Jira keys may not exist yet:

```text
features/<control-id>/
  feature.md        feature and user stories (FR-SDLC-002)
  design.md         design specification (FR-SDLC-003)
  plan-<repo>.md    implementation plan, one per target repository (FR-SDLC-006)
  links.yaml        results of the agents' writes: Jira keys, Confluence pages, pull requests, each with the
                    artifact commit it came from, the run, the acting identity and the time
records/<yyyy>/<mm>/<run-id>.md
                    unattended writes that need no approval: review findings, incidents, bugs (FR-TRIG-003)
```

Every artifact has front matter with its control ID, team, kind, the run that drafted it, the previous artifact's
path and commit (if it was published), and the Jira keys once they exist.

## Drafting: the user's own artifacts

- user_agent saves drafts, review results and later drafts as the user's own artifacts. The user can move to the
  next step (features to design, for example) starting from their own artifact; nothing is checked on
  sdlc-control and nothing is written to another system.

## Publishing: when the user asks for a write

1. The user asks for a write: add the feature and stories to Jira, publish a page to Confluence, or hand a design
   to implementation.
2. The agent commits the artifacts the write rests on (and any earlier unpublished ones it depends on, such as
   the feature behind a design) on a branch `sdlc/<control-id>/<kind>` and opens a pull request on the team's
   control repository, as the user with their own connection. The review loop's findings and the user's choices
   go into the description.
3. The run shows the pull request link and waits as a human task ([FR-HUM-001](../requirements/functional/FR-HUM-001.md)).
4. **Approved** means: the artifact is on the control repository's main branch, and the last commit that changed it
   there came from a pull request merged by a person, not by a system identity. Branch protection decides who
   may merge.
5. The agent makes the write, then records its keys and links in `links.yaml`.

The tool that writes to Jira, Confluence or a repository takes the control ID and artifact path, and the MCP
server refuses (`not_approved`) unless that artifact is approved on the run's team's control repository.

## Steps that start from published items

| Step | Starts from | Check on sdlc-control main |
|---|---|---|
| Features and stories (user_agent) | an idea, ticket or bug | none |
| Design specification (user_agent) | the user's own feature artifact | none |
| | or a Jira feature | its `feature.md` with the feature's key in `links.yaml` |
| Hand-off of a design | the user asks for it | the design is published as `design.md`; its merge starts ci_workflow_agent |
| Implementation plan (ci_workflow_agent) | a merged `design.md` | `design.md` |
| Implementation (ci_workflow_agent) | a merged `plan-<repo>.md` | the plan; then the product repository pull request, recorded in `links.yaml` |

No step depends on a Jira status (the user's change of 2026-11-25): approval on the control repository is the
only gate.

The event-based agents only act on other systems, so their artifacts always go through sdlc-control: plans by
pull request and merge, and unattended writes that need no approval (findings as pull request comments or Jira
tasks, incidents, bugs) as a `records/` file committed before the write, with its results after it.

## Recording the results

- `links.yaml` and `records/` are committed directly to main. Branch protection must let the acting identities
  push to those paths only; `feature.md`, `design.md` and `plan-*.md` change only by pull request. A write whose
  result never landed shows as an artifact without links.
- The [Audit Log](../components/audit-log.md) still records every tool call and authorization decision;
  sdlc-control is the record people read.

# Consequences

- Supersedes the hand-off of [DEC-0008](DEC-0008.md): approved features and stories still go to
  Jira, but approval is a merge on sdlc-control instead of chat, the design is no longer a pull request on a
  product repository, and ci_workflow_agent starts from merges on the control repository. `design_path` on
  product repositories goes away.
- Requirements changed with the acceptance:
  - [FR-SDLC-001](../requirements/functional/FR-SDLC-001.md): approved artifacts live in the team's control
    repository; steps that start from published items check them there.
  - [FR-SDLC-002](../requirements/functional/FR-SDLC-002.md): drafts stay the user's own; Jira issues only after
    `feature.md` is merged, keys recorded.
  - [FR-SDLC-003](../requirements/functional/FR-SDLC-003.md): starts from the user's own feature artifact or a
    published feature.
  - [FR-SDLC-005](../requirements/functional/FR-SDLC-005.md): the design pull request is on the control
    repository; its merge starts ci_workflow_agent.
  - [FR-SDLC-006](../requirements/functional/FR-SDLC-006.md): plans on the control repository; implementation
    pull requests after their merge, links recorded.
  - [FR-SDLC-010](../requirements/functional/FR-SDLC-010.md), [FR-SDLC-012](../requirements/functional/FR-SDLC-012.md)
    and [FR-TRIG-003](../requirements/functional/FR-TRIG-003.md): unattended writes recorded in `records/` first.
  - [FR-HUM-005](../requirements/functional/FR-HUM-005.md): for writes to other systems, the approval bound to the
    write is the merge, checked by the MCP server. Separation of duties
    ([FR-HUM-004](../requirements/functional/FR-HUM-004.md)) can be enforced by branch protection (a required
    reviewer other than the author).
  - New: [FR-SDLC-013](../requirements/functional/FR-SDLC-013.md), the control repository (layout, approval check, results recorded).
- Configuration ([FR-CFG-001](../requirements/functional/FR-CFG-001.md)): team systems are part of each
  environment's `teams.yaml`. Tool groups for the control repository tools (read,
  publish, record) in user_agent_mcp and event_agent_mcp.
- Connections: every user who publishes needs a connection with write access to their team's control
  repository ([FR-CONN-001](../requirements/functional/FR-CONN-001.md)); so does the system identity.
- The event gateway subscribes to merges on each control repository's main branch under `features/`.
- Phase 4a milestone 3: drafts stay the user's; on request, `feature.md` goes to the control repository, and
  after the merge the Jira issues follow; the design is published the same way. Exit gate: a published feature
  merged on a test control repository, its Jira issues created and recorded in `links.yaml`, then a published
  design merged there.
