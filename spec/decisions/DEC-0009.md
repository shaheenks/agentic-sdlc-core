# Context

sdlc_ui sits behind Identity-Aware Proxy, which adds a signed token (the `x-goog-iap-jwt-assertion` header)
naming the user to every request. Using that token as the user's identity for the agents and user_agent_mcp
would avoid sdlc_ui's second sign-in ([DEC-0001](DEC-0001.md)). Gemini Enterprise, the other first-phase
surface, does not pass through IAP and supplies a Google account token.

# Options

## A. The IAP signed token as the user's identity

- For: no second sign-in or OAuth client for sdlc_ui.
- Against: it is issued for sdlc_ui's audience and lives only minutes; once forwarded beyond sdlc_ui it is a bearer
  assertion that IAP no longer vouches for, so every service accepting it must also restrict its callers; Gemini
  Enterprise cannot supply one, so the platform would need two identity paths.

## B. Google account tokens on every surface, IAP as the perimeter only (accepted)

- For: one kind of user token for sdlc_ui and Gemini Enterprise, verified one way; a standard OAuth token with a
  lifetime that fits a session.
- Against: sdlc_ui keeps its second, silent sign-in and its OAuth client.

# Decision

**B**, accepted by the user on 2026-11-24.

- sdlc_ui (through its own OAuth client) and Gemini Enterprise (through its authorization) both supply the user's
  Google account token; the agents forward it to user_agent_mcp, which verifies it through
  [Identity](../components/identity.md).
- The IAP signed token only gates access to sdlc_ui: the BFF verifies it on every request and never forwards it.

# Consequences

- [DEC-0001](DEC-0001.md) stands as written.
- Identity verifies one kind of user token for every surface.
