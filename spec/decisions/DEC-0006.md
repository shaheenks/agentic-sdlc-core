# Context

Users' connection secrets need a store that keeps each user's secrets visible only to that user
([FR-AUTHZ-008](../requirements/functional/FR-AUTHZ-008.md)). The platform already has a per-user store, the
artifact bucket, which the MCP servers reach through a mount point. This record keeps user connection secrets
there for now, to be reviewed later.

# Options

## A. GCP Secret Manager for every secret

- For: built for secrets; IAM, versions and access audit per secret; Secret Manager is the usual answer in a review.
- Against: a second store and client next to the bucket; one secret per user and provider to manage.

## B. A `secrets/` prefix of the artifact bucket, through a mount (accepted for now)

- For: one store for everything a user owns; plain file reads and writes through the mount; the same code runs
  locally against a folder.
- Against: access is granted per bucket or prefix, not per secret, so a service account that may read
  `secrets/users/` reads every user's encrypted PATs, and isolation between users rests on the server's own
  code and the encryption key; reads are
  audited only if Cloud Storage Data Access audit logs are on; the mount has no locking, so concurrent writes to one object keep the last.

# Decision

**B**, set by the user on 2026-11-22, for now and to be reviewed later.

| Prefix | Holds | Lifecycle | Used by |
|---|---|---|---|
| `artifacts/users/<user ID>/` | A user's artifacts | Deleted 7 days after creation | user_agent_mcp |
| `artifacts/system/` | Artifacts of scheduled and event-triggered runs | Deleted 7 days after creation | event_agent_mcp |
| `secrets/users/<user ID>/` | One object per provider: the PAT and connection metadata, encrypted by the application | None | user_agent_mcp |

- The user ID is the stable Google account ID (`sub`) from the verified token; the server builds every path from
  it and never from a tool argument.
- user_agent_mcp and event_agent_mcp mount the bucket as a Cloud Run Cloud Storage volume at the path in their
  `STORE_MOUNT_PATH` environment variable. IAM conditions on object names limit each service account to its own
  prefixes (user_agent_mcp: `artifacts/users/`, `secrets/users/`; event_agent_mcp: `artifacts/system/`). No other
  component mounts or reads the bucket.
- Only users' connection secrets are in the bucket. System connection
  secrets, webhook signing secrets and OAuth client secrets stay in GCP Secret Manager and reach the services
  that need them (the event gateway, event_agent_mcp, sdlc_ui) as environment variables through Cloud Run
  secret references.
- **Encryption at the application:** before writing, user_agent_mcp encrypts each secret object with AES-256-GCM under a data-encryption key it reads from GCP Secret Manager, with the user ID and provider as associated data; the object records the key version, and the key is never written to the bucket or a log. Copying an object to another
  user's path makes it undecryptable, so a path mistake cannot hand one user's PAT to another.
- No rotation of the data-encryption key and no Data Access logging on the bucket for now (confirmed by the
  user on 2026-11-24, together with keeping artifacts and secrets in the artifact bucket scoped to each user).
- Locally the mount point is a git-ignored folder (`local` profile) or the development bucket through Cloud
  Storage FUSE (`gcp-dev` profile).

- [NFR-SEC-004](../requirements/non-functional/NFR-SEC-004.md), [FR-CONN-001](../requirements/functional/FR-CONN-001.md),

- The lifecycle rule matches the `artifacts/` prefix only.
- Review before PATs of users outside the development team are stored, or before production, whichever is first.
