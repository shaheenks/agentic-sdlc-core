# Context

[DEC-0011](DEC-0011.md) ingests `git` sources, and a private repository is read with a token from Secret Manager
(`credential`). The ingest pipeline always sends that token as HTTP Basic with the username `x-access-token`, which is
what GitHub expects. Bitbucket refuses it:

- **Bitbucket Cloud** repository, project and workspace access tokens sign in with the username `x-token-auth`; API
  tokens sign in with the Bitbucket username of the account that owns them.
- **Bitbucket Data Center** HTTP access tokens sign in either as `Authorization: Bearer <token>` (personal, project
  and repository tokens) or as HTTP Basic with the owning user's username (personal tokens only).

So today only public Bitbucket repositories can be knowledge sources, and the example configuration says so
(`config/env/example/sources/platform-wiki.yaml`, `ledger-docs.yaml`). On 2026-11-26 the user asked for private
Bitbucket sources.

# Options

## A. Choose the sign-in from the host only

`github.com` and other hosts: Basic `x-access-token`; `bitbucket.org`: Basic `x-token-auth`; nothing to configure.

- For: no new configuration.
- Against: a Data Center or GitHub Enterprise host is just a host name, so the pipeline cannot tell which scheme it
  wants; API tokens on Bitbucket Cloud need a real username, which cannot be guessed.

## B. The source may declare its sign-in; defaults follow the host (recommended)

Two optional keys on a `git` source with a `credential`:

- `credential_scheme`: `basic` (default) or `bearer`.
- `credential_username`: the Basic username. Default: `x-token-auth` for `bitbucket.org`, `x-access-token` for every
  other host. Not allowed with `bearer`.

- For: every token kind on GitHub, Bitbucket Cloud and Data Center is covered; existing sources and the common
  cases (GitHub tokens, Bitbucket Cloud access tokens) need nothing new.
- Against: two more keys, and a wrong choice shows only when ingest runs.

## C. A source kind per host (`github`, `bitbucket_cloud`, `bitbucket_dc`)

- For: matches the connectors' providers, and links could default per host.
- Against: three kinds for one fetch (a git clone), and a schema change for every existing source.

# Decision

**B**, accepted by the user on 2026-11-26, and built.

- **Schema:** `credential_scheme` (`basic` | `bearer`) and `credential_username` (pattern
  `^[A-Za-z0-9._@+-]{1,100}$`) on a source; validation refuses either without `credential`, and `credential_username`
  with `bearer`.
- **Ingest:** the token is still read from Secret Manager (`INGEST_SECRET_<NAME>` locally) and passed in an HTTP
  header through git's environment, never in a URL, command line or the clone's configuration; only the header's
  scheme and username change. Errors never contain the token; they name the source and the HTTP refusal.
- **Username:** it is not a secret. It is an account name, though, so a source using a personal account's username
  belongs in the git-ignored environment configuration, never in the committed example; the example shows an access
  token (`x-token-auth`) and a Data Center `bearer` source.
- **Examples:** `platform-wiki.yaml` and `ledger-docs.yaml` become private sources with a `credential`, one with the
  default username and one with `credential_scheme: bearer`.

# Consequences

- FR-KNOW-001 gains an acceptance criterion: a private `git` source on GitHub, Bitbucket Cloud or Bitbucket Data
  Center is read with its declared or the host's default sign-in.
- Code: `config/schemas/sources.schema.json` and its validation; `knowledge_ingest` `fetch_git` builds the header from
  the scheme and username; tests for each host's default, `bearer`, and the refused combinations.
- The ingest service account reads one more secret per private Bitbucket source; the user creates each secret and
  grants the ingest service account access, as for GitHub today.
- Everyone given a source still sees everything its token can read ([DEC-0011](DEC-0011.md)); a Bitbucket token for
  ingest should be a read-only repository or project access token, not a person's token.
