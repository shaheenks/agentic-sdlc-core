# Context

The platform needs to keep runs, tasks, artifacts, connections, configuration and audit records. A relational
operations database would hold most of that, but it adds a service to run, back up and keep highly available
across zones. The user decided on 2026-11-22 not to build one now and to reconsider later.

# Options

## A. Operations database now

- For: queries across runs and users, exact rate limits and budgets, one place for run history.
- Against: another stateful service to run highly available in europe-west3; schema and migrations before the
  first workflow runs.

## B. Managed stores only, database later (accepted)

- For: every kind of state goes to a managed service Google already runs across zones; nothing to migrate yet.
- Against: some features are approximate or deferred until a database exists (below).

# Decision

**B**, accepted by the user on 2026-11-22.

| State | Where it lives |
|---|---|
| Configuration bundles | The dedicated configuration bucket ([FR-CFG-005](../requirements/functional/FR-CFG-005.md)) |
| Artifacts | The dedicated artifact bucket, deleted after 7 days ([FR-ART-003](../requirements/functional/FR-ART-003.md)) |
| PATs and other connection secrets, with connection metadata | The artifact bucket's `secrets/` prefix, through a mount, for now ([DEC-0006](DEC-0006.md)) |
| Platform secrets (OAuth client secrets, webhook signing secrets) | GCP Secret Manager ([NFR-SEC-004](../requirements/non-functional/NFR-SEC-004.md)) |
| Runs: graph state, step outputs, waiting human input, transcripts | Agent Runtime Sessions, one session per run, labelled with workflow, team, surface and trigger ([DEC-0004](DEC-0004.md)) |
| Run history and task inbox | Listed from Agent Runtime Sessions by the caller's user ID only ([FR-AUTHZ-008](../requirements/functional/FR-AUTHZ-008.md)) |
| Audit records | Structured OpenTelemetry logs in Cloud Logging, 30-day retention |
| Trigger deduplication | A conditional create (only if absent) of one object per delivery ID in a small bucket |
| Membership and policy caches | In memory, per service instance |
| Knowledge | The knowledge graph backend's own store, which is part of the isolated knowledge services, not an operations database |

# Consequences

- Rate limits and quotas ([FR-AUTHZ-005](../requirements/functional/FR-AUTHZ-005.md)) are counted per service
  instance, so they are approximate.
- Model budgets ([FR-MDL-002](../requirements/functional/FR-MDL-002.md)) are reported from Cloud Monitoring
  metrics; refusing calls over a budget is parked until a database exists.
- Cross-run reports beyond what session listing gives (for example, all failed runs of a workflow last month)
  come from logs and metrics, not queries.
- Revisit when any of these is needed: exact quotas or budgets, run queries across users, artifact retention
  beyond 7 days, or session listing that is too slow at the volumes seen.
